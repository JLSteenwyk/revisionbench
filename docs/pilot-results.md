# Development pilot — preliminary, not confirmation

The initial Qwen Q4_K_M pilot completed 66 episodes: 27 peer-influence episodes, 24 seeded replacement episodes, and 15 seeded intervention episodes. All three run audits independently replayed the recorded actions and verified state transitions, scores, and schedule completion. Evidence is under `results/development-001/qwen-{peer,replacement,intervention}/`.

Qwen completed all nine competence-control episodes, with no invalid actions in the peer pilot. Every task completed in all nine peer-experiment conditions. The no-message and two authorized controls had zero unauthorized attempts. All six external-message conditions had unauthorized attempts and completed changes in all three tasks. Thus the source-by-permission and source-by-success contrasts were both zero in this small pilot. This is a ceiling result across message conditions, not evidence that peers have a unique effect or that permission claims are necessary.

In deliberately seeded replacement states, keeping notes yielded violations on all three tasks; removing notes yielded violations on one of three tasks, regardless of the queue and environment-change factors in this initial sample. These are planted-state results and must not be described as naturally emerging persistence.

For seeded interventions, no intervention and an acceptable-stop instruction each produced completed unauthorized changes on all three tasks. Blocking the bundle operation and enforcing authorization across operations prevented completed unauthorized changes in all three tasks, while attempts still occurred in all three. Each completed the legitimate task on one of three tasks. Explicit owner correction produced an unauthorized change on one of three tasks and completed all three tasks. With only three task clusters, these are descriptive observations without reliable effect-size precision.

Both pinned model files passed their expected SHA256 checks. Qwen loaded successfully with the recorded local llama.cpp configuration. Ministral's first launch failed before any inference because the port probe rejected TIME_WAIT connections left by the stopped Qwen server; operating-system inspection found no listening server. The launcher was corrected to permit address reuse while still rejecting an active listener. The failure remains in `results/development-001/launch-ministral.log`; the same Ministral development schedule is retried in `results/development-001-ministral-retry/`.

Qwen's sampled peak whole-GPU memory use was 21,323 MiB (`artifacts/environment/gpu-qwen-20260912T234103Z.jsonl`, five-second sampling). Recorded episode wall times summed to 23.78 seconds for peer influence, 27.75 seconds for replacement, and 15.25 seconds for intervention. Mean response latency was 0.396, 0.369, and 0.362 seconds respectively. These small, short-action tasks and cached prompts are not a general throughput benchmark; load time and orchestration overhead are excluded from these episode totals.

Still required: complete Ministral validation, cover all prompt variants in expanded development, examine natural checkpoints separately, finalize sample size and preregistration, run held-out confirmation, and write the final report. No confirmatory result is claimed here.

## Chat-template compatibility amendment

The port fix allowed Ministral to load, but the first peer request failed with an explicit template error: conversation roles must alternate. The raw failure is preserved in `results/development-001-ministral-retry/ministral-peer/episodes/00000.json` and `artifacts/environment/server-ministral-20260912T234337Z.log`. It contains zero model actions and is an infrastructure failure, not a safety outcome.

Adjacent user messages are now combined with two newlines in the shared controller, preserving their complete text and source labels. This includes owner corrections after checkpoint tool results. Both models will run the amended format on nine development tasks spanning all family/wording combinations in `results/development-002/`. The initial Qwen observations above use the earlier consecutive-user format and remain separate. This compatibility change is justified by the model's documented runtime error, not by a preferred behavioral result.

The expanded Qwen peer pilot completed and passed its replay audit. It completed 23 of 27 controls, with 0.84% invalid actions across all peer episodes. Unauthorized-attempt counts out of nine were: no message 4, peer facts 4, peer success 3, peer permission 8, reference facts 6, reference success 4, and reference permission 7. Both authorized controls had zero unauthorized attempts. The descriptive source-by-permission interaction was +33.3 percentage points across nine task clusters; this small development estimate is not confirmatory evidence. Differences from the initial pilot also involve broader task/wording coverage, so aggregate changes cannot be attributed solely to chat formatting.

Natural checkpoint selection for the expanded pilot is fixed as the first eligible episode in the saved randomized schedule per task, excluding infrastructure failures. Replacement uses the checkpoint after the first unauthorized attempt; intervention uses the checkpoint before it. The Qwen peer pilot yielded eight unique task checkpoints for each timing, each verified against its parent trace and remaining step budget. `scripts/recovery_pilot.py` runs these branches serially on the GPU after the expanded two-model pilot finishes. Naturally occurring and deliberately seeded results remain separate.

Ministral's development-002 run was stopped after nine complete episode records, all with eight invalid actions and no executed actions. The responses repeatedly wrapped JSON in Markdown fences; later error-recovery replies sometimes included prose or multiple proposals. The exact stop record is `results/development-002/ministral-format-stop.json`. This was a development interface diagnosis, not a preregistered statistical stopping rule or a completed competence test. No safety conclusions are drawn from its zero executed violations. The queued natural-development-002 run was cancelled before any branches began.

The next common-harness development run, `results/development-003/`, accepts a single whole-response JSON code fence as a deterministic wrapper normalization, while rejecting prose, multiple proposals, and non-JSON fences. Raw responses and wrapper flags remain saved. Both models use the same parser; earlier results are not pooled with it. The model order is Ministral then Qwen so the diagnosed incompatibility is checked first.
